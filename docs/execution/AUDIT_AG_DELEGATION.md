## 4. A〜Gの合格条件

原指摘、実コード、再現証拠を照合する。指摘を無条件に正しいとせず、反証は根拠付きで独立確認を受ける。観測スクリプトのexit0を不具合解消の証拠にしない。

### A：古いスタッフ設定フォーム

- 対象スタッフの設定版をUI→Schema→API→トランザクションで検査し、古い保存は409で拒否。
- 無効化、Permission剥奪、店舗削除、Role変更を古いフォームから復元しない。表示名を含め更新対象を原子的に保存する。
- 操作者の認可と編集対象の競合は別問題。両方検査する。
- 既存revision/triggerを確認し、複数回増える版をクライアントが+1と推測しない。ログイン時刻の変化まで無用な設定競合にしない。
- 409で新しい版へ自動差替え・自動再送しない。最新内容の再読込から編集する。
- 2管理者の通常画面/API/実DBで両順序、無効化・剥奪・店舗削除、古い名前編集、再読込後の正規保存、部分更新なしを検証する。

### B：権限取消中の台帳書込み

- 在庫ロック待機中に権限取消が先にcommitしたなら、待機していた登録／更新を保存しない。
- 再SELECT直後の取消競合も含め、認可・書込み・取消の順序と失敗時処理を定義する。単にもう一度読んだだけで原子的と主張しない。
- 担当外・権限外の早期拒否、対象version、店舗制約、監査を維持。
- 認証と台帳の接続分離を維持し、台帳用接続にスタッフ情報の広いSELECTを戻さない。認証用接続で台帳を書かない。
- 複数接続を使うだけで単一トランザクションとは言わない。長い在庫待ちが取消・ログインを塞がないロック順と接続解放を設計。
- 新たな特権付与が不可避な箇所は承認待ちとして分離し、他の独立項目を続ける。
- 実Postgres同期点を用い、Permission剥奪・店舗削除・無効化・逆順開始・正常登録更新・不要ロックなし・接続残留なしを検証する。

### C：期限切れHOLDのclaim

- 失効してよい未決済HOLDと台帳の整備／数量変更を整合させ、無関係な次のHOLD書込みや常駐処理の偶然実行に依存させない。
- PENDING/UNKNOWN/SUCCESS、準備・発送固定、貸出・有効な将来割当を時間だけで解除しない。claim一括削除や保護trigger撤去は禁止。
- 通常API/実DBで、期限切れ後の正常変更、有効な保護の拒否、新規HOLDとの競合、ポール数量の整合、監査を検証する。

### D：参照のないREADY移動

- 実受領・準備完了後に保護不要になった移動は、別のtransfer.addを待たず整合・完了できるようにする。
- 参照HOLDあり／なし、部分受領、未着、要対応を区別。発送・受領履歴、再送識別を削除しない。
- 完了処理でポールのprojection・仮想slice・実数量を二重加算しない。依存claimを無視して閉じない。
- 個体／数量の正常完了、台帳調整、将来HOLD、同時受領・新規確保、再送、参照付き保護を実DBで検証する。
