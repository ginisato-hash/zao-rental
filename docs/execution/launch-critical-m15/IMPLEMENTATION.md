# M1.5 normal runtime composition

One trusted server bootstrap installs a validated ProductionRuntime input before Next instrumentation exposes routes. Inputs are server-owned configuration, an independently approved configuration digest and deployment identity, separate secret roots, exact least-privilege DB bindings, and a provider-attested peer callback. No environment URL, owner connection, credential chain or request header grants activation. NODE_ENV alone does not activate this composition. An explicit marker without installed inputs fails startup; failures latch without development/Preview fallback.

The default Neon connector requires actual authenticated client TLS (hostname, certificate, protocol and channel binding) and SQL identity/role checks. Tests replace only this connector with owned local PostgreSQL pools and inject clearly synthetic provider metadata; those tests do not prove actual Neon/Vercel Production identity. Auth/ledger/HOLD/transfer/pricing/recommendation/operations/guest/content/Avatar/BookingAccess roles remain distinct, with existing maintained auth and domain services. No migration or historical SQL change is required.

Normal guest, access/recovery, staff and private derivative routes use the composed runtime. Avatar defaults OFF; media/Avatar OFF do not remove guest recommendation/HOLD/quote or canonical payment-state/access readers. Media reads use the existing private R2 adapter and rights checks before/after delivery; the exposed runtime has no upload/purge/signing method. Later credential revocation or read failure degrades presentation only. Startup requires a valid explicit media binding if that feature was requested.

Payment accepts an explicit SQUARE_PRODUCTION port only after validating separate Production credential material/provenance and exact merchant identity. Sandbox/absent bindings fail startup, and bootstrap makes no provider call. The existing booking/payment state machine and commercial activation gates are unchanged: no simulated checkout in Production, no claim that configuring this port authorizes a real charge. The safe component state is CONFIGURED_ACTIVATION_PENDING. The external connection/activation phase must supply and authorize the actual provider implementation; no provider SDK or contract was selected here.

BookingAccess and BookingRecovery use independent supplied signing roots and existing expiry/revocation/hash-only records. Recovery delivery remains explicitly UNCONNECTED until a provider-neutral delivery binding is installed. M1.6 supplies the durable local delivery core. Neither the anonymous readiness route nor fixed startup failures exposes identifiers, credentials, URI, PII or raw provider errors. Component diagnostics require the maintained all-store admin STAFF_MANAGE permission. Existing /api/health remains liveness; /api/readiness reflects required bootstrap completion, not proof of a commercial launch gate.

## Verification boundaries

The new PG matrix checks actual role/DB mismatch, partial-startup pool disposal, absent/Sandbox payment credentials, Avatar/media OFF, existing confirmed fixture booking/HOLD/quote/payment-state/QR continuity, unconnected recovery, private R2 fixture timeout and credential revocation, and root separation. The normal built Next browser runs with NODE_ENV=production, synthetic verified dispatcher metadata, an owned local TLS server and local roles only. It checks390/1440px, fresh guest recommendation, existing confirmed booking/quote/HOLD/payment read state, capability issuance/QR, fixed anonymous readiness and staff-only details, disabled Avatar404, optional503 degradation and exact business-row fingerprints. Fixture payment is completed locally before the Production-configured server starts; no Production payment is implied.

Actual Production deployment, real credentials, hosted DB, Square, R2, mail/SMS and provider mutation remain0. Actual provider verification/connection and commercial activation are future gates. No main merge.
