## What this adds

- [scripts/production-backup.ts](../../../scripts/production-backup.ts) — the backup mechanism: env validation and fail-closed host/bucket checks, `pg_dump -Fc` via env-only libpq config (`PGSSLMODE=verify-full`, `PGCHANNELBINDING=require`, bounded `lock_timeout`), `pg_restore --list` structural validation, `age` public-key encryption (via the official `age-encryption` JS package, not a shelled-out binary), R2 upload via the existing `@aws-sdk/client-s3` dependency, deterministic `hourly/`/`daily/` object keys, and a single top-level `finally` that always removes the plaintext temp file regardless of where the pipeline fails.
- [tests/readiness/production-backup.ts](../../../tests/readiness/production-backup.ts) — 20 dependency-injected logic tests (env/host/bucket validation, fail-closed behavior at every pipeline stage, plaintext cleanup, redaction, symlink rejection, deterministic keys/daily-promotion, static checks of the workflow YAML, and Worker dispatch-target/token-logging checks), plus a 21st synthetic end-to-end dump→encrypt→decrypt→restore proof against an isolated local PostgreSQL 18 fixture, gated on `pg_dump`/`pg_restore` being present.
- [.github/workflows/production-backup.yml](../../../.github/workflows/production-backup.yml) — `workflow_dispatch`-only, `contents: read`, dedicated non-cancelling concurrency group, an activation gate (`main` + `vars.PRODUCTION_BACKUP_ACTIVATION == 'R4_APPROVED'`) that skips before any Production secret reference executes, and a job container pinned to `postgres:18@sha256:86c951e05bf56c93d95d397747fb8820ac76cc3bedb78f43abd83eedbe3666ae` (resolved live from `registry-1.docker.io` on 2026-09-21; corresponds to the `18.6` release per the image's own annotations) so `pg_dump`/`pg_restore` are a pinned PostgreSQL 18, not whatever the runner happens to preinstall.
- [apps/backup-scheduler-worker/src/index.ts](../../../apps/backup-scheduler-worker/src/index.ts) and [wrangler.toml](../../../apps/backup-scheduler-worker/wrangler.toml) — the future Cloudflare Worker Cron scheduler. Fixed dispatch constants (repo/workflow/ref), no `fetch()` handler (no public endpoint), never logs the dispatch token. `wrangler.toml`'s `[triggers]` block is commented out and no `wrangler deploy` was run — the Cron Trigger is not active.
- `package.json` / `scripts/verify.mjs` — added the `age-encryption` dependency (pinned `0.3.1`, the official FiloSottile/typage JS implementation — chosen over shelling out to an `age` CLI binary that isn't guaranteed present, and over any unofficial npm wrapper), `backup:production` and `test:production-backup` scripts, and wired `test:production-backup` into the Foundation verify sequence.
- `tsconfig.json` — added `apps/backup-scheduler-worker/**/*.ts` to `include`.

## What this deliberately does not do (still zero in this phase)

No Production DB connection, no SQL, no backup DB role, no DB password, no R2 credential, no GitHub `production-backup` environment secret, no Worker secret, no Cron activation, no Production deploy, no Square/payment/inventory/DNS action. The `PRODUCTION_BACKUP_ACTIVATION` variable does not exist, so the one workflow job that would touch Production secrets is architecturally unreachable until a separate R4 authority creates it. The GitHub `production-backup` Environment itself was **not** proactively created via API in this pass (the authority marks this "may", not "must"; the workflow's own `environment: production-backup` key will create it automatically the first time the job body actually runs, which activation-gate design ensures cannot happen before R4).

- `npx tsc --noEmit`: clean.
- `npx eslint <new files> --max-warnings=0`: clean.
- `npm run check:secrets`: PASS, 2309 files scanned (one initial false positive from a synthetic user:pass@host connection-string literal inside the test file's own redaction test was fixed by constructing that string at runtime instead of as a static literal).
- `npm run check:reference`: PASS.
- `npm run test:production-backup`: **20/20 logic-level cases PASS.**
- **Mutation test performed and reverted**: the top-level `finally` cleanup block in `runProductionBackup` was temporarily replaced with a no-op; `npm run test:production-backup` then failed exactly at the plaintext-cleanup assertion (test 6, `AssertionError: Missing expected rejection` on `access(plaintextPath)`), proving the dedicated test genuinely catches that regression. The file was restored from an untouched copy immediately afterward and the full 20/20 PASS was reproduced again.
- **Case 21 (synthetic dump→encrypt→decrypt→restore against a real isolated PostgreSQL 18 instance) is SKIPPED in this sandbox**, not PASS: this development environment has no `pg_dump`/`pg_restore`, no Docker, no Homebrew, and no package manager to install PostgreSQL 18 client tools, and none of `embedded-postgres`'s bundled platform binaries include them (only `initdb`/`pg_ctl`/`postgres`). The test detects this via a live `pg_dump --version` probe and prints a loud `SKIP ...` line rather than silently passing. The pinned `postgres:18` container job in `production-backup.yml` provides `pg_dump`/`pg_restore` in CI, where Foundation CI (triggered by this Draft PR) will exercise Case 21 for real. This gap is disclosed here rather than claimed as passing.
- `npm run verify` (the full Foundation suite, all existing test commands plus the new one): see the PR submission comment for the outcome — it was run to completion in the background from this same worktree and its result is reported there rather than duplicated here, to avoid this document going stale if it is read before that run finishes.
