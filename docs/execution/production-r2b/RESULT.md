## R2B-F1–F7 (PR #27 review `5763014617`) — how each was addressed

- **F1 streaming encryption**: `encryptFileToFileStreaming` streams plaintext → age ciphertext file-to-file via the `age-encryption` Streams API (`Readable.toWeb`/`Writable.toWeb`, no whole-buffer `Uint8Array`). Plaintext SHA-256 is computed by a hashing `Transform` inline in the read pipeline, not a separate full read. Both the plaintext and ciphertext temp files are removed in the orchestrator's single `finally`, on every path including success. The file no longer imports `readFile` from `node:fs/promises` at all; test 27 statically asserts that import is absent, so a regression back to whole-buffer processing is caught automatically. Verified locally: a ~2.3MB smoke test and test 28's ~1.4MB round trip both match plaintext SHA-256 exactly and decrypt correctly.
- **F2 Go-age interoperability**: `tests/readiness/production-backup.ts` downloads the official `FiloSottile/age` v1.3.2 release for the running platform (Node's built-in `fetch`, no curl-pipe-shell), verifies its SHA-256 against a pinned constant before ever extracting/executing it, and proves both directions: R2B-encrypted → official `age -d` decrypts correctly, and official `age -r` encrypted → `age-encryption`'s `Decrypter` decrypts correctly. A disposable identity is generated via the official `age-keygen` for each run and never reused. **This ran for real in this session** (darwin-arm64) and passed both directions; the linux-amd64 checksum used for CI was independently re-verified byte-for-byte against `cbe24006683f8eb669266162894b9a522a1af52f2665fbc63a4bb032ed26ac10` before being pinned.
- **F3 mandatory PG18 proof, no silent CI skip**: the actual Foundation CI run on the pre-fix HEAD (`35616862960`) failed with `pg_dump exited 1` — Ubuntu 24.04's ambient `pg_dump` is not major 18, and the test used to accept "present" as good enough. The test now resolves a `PgToolRunner`: it checks the ambient tool's major version via `pg_dump --version`; if not exactly 18 it falls back to invoking the pinned `postgres:18@sha256:...` image through `docker run --rm --network host` (host networking so the container reaches the local isolated Postgres fixture), re-verifying that image's own `pg_dump --version` also reports 18 before trusting it. If `CI=true` and neither path is available, the test **throws and fails** (verified locally by re-running with `CI=true`: it now fails with `BACKUP_TEST_PG18_PROOF_UNAVAILABLE_IN_CI`, not a silent pass). Only outside CI (this local macOS sandbox, no Docker) does it SKIP, loudly. The Docker code path itself could not be exercised locally (no Docker in this sandbox) — its correctness will be confirmed by the next Foundation CI run, which is why this resubmission waits for that SUCCESS before re-posting the report.
- **F4 exact Production host identity binding**: `assertProductionHostFingerprint` compares SHA-256(lowercased, trimmed `PGHOST`) against a committed constant (`EXPECTED_PRODUCTION_HOST_FINGERPRINT_SHA256 = 7ad9939654fde65fa8bf8c4c043e33ca9053036d2137cf7616d365a11876c3fc`, as given by TD), on top of the existing shape/pooled/non-Neon checks, plus a new `assertProductionPort` requiring exactly `5432`. The expected fingerprint is a function parameter defaulting to that real constant — never sourced from an env var — so the CLI entrypoint always enforces the real value while tests can supply their own self-computed fingerprint for a synthetic host to exercise both the accept and reject paths without ever needing to know the real Production hostname (test 23). A different syntactically-valid `.neon.tech` host is proven rejected. The real fingerprint constant is encoded exactly as TD provided; it was not independently re-derived from a live Neon endpoint in this pass (no Neon credential is available, and doing so would mean discovering the real hostname, which this pass deliberately avoids).
- **F5 scheduler-authoritative timestamp**: `parseScheduledAt` strictly validates a canonical `Z`-suffixed ISO 8601 string (test 25 covers missing/malformed/offset-form rejection) and is now *required* by `runProductionBackup` (no `now()`/wall-clock fallback exists in the orchestrator at all). The Worker's `scheduled()` converts Cloudflare's `scheduledTime` (epoch ms) to that canonical ISO and sends it as the `workflow_dispatch` input `scheduled_at` (test 21); the workflow passes it through as `SCHEDULED_AT`. Because `objectKey`/daily-promotion were already pure functions of the timestamp, a retry with the same `scheduledAt` now provably reuses the same object key (test 26) — no extra retry-specific logic was needed once the authority source was fixed.
- **F6 minimal child env**: `minimalPgChildEnv` builds an explicit allow-list (`PATH`, `HOME`, `LANG`, `LC_ALL`, `TMPDIR`, `TEMP`, `TMP`) plus only the caller-supplied PG/security vars; `spawnPgDump`, `spawnPgRestoreList`, and the version probes all use it instead of `...process.env`. Test 22 proves a synthetic unrelated "secret" placed in the source env never reaches the constructed child env.
- **F7 strict BACKUP_CLASS parsing**: `parseBackupClass` accepts only the literal strings `'hourly'`/`'daily'` and throws `BACKUP_CLASS_INVALID` for anything else (including case variants); the CLI entrypoint now calls it instead of the previous `=== 'daily' ? 'daily' : 'hourly'` silent coercion. Test 13 covers this directly.

## R2B-F8 (PR #27 addendum `5763893376`, execution directive `5764632325`) — explicit libpq CA root for `verify-full`

Neon's secure-connection documentation (https://neon.com/docs/connect/connect-securely) states that a libpq client using `sslmode=verify-full` must be given a trusted root certificate path via `PGSSLROOTCERT`; the prior HEAD set `PGSSLMODE=verify-full` and `PGCHANNELBINDING=require` but never supplied one, so it would have relied on whatever ambient/accidental root the pinned runtime happened to have.

- **Fixed Production CA root**: `EXPECTED_PRODUCTION_CA_ROOT = '/etc/ssl/certs/ca-certificates.crt'` — the documented Debian/Ubuntu system bundle, matching the pinned `postgres:18` Production Backup runtime. Declared as a constant, never read from an env var.
- **Pre-spawn fail-closed validation**: `assertCaRootUsable(path, accessCheck?)` runs inside `spawnPgDump` *before* the `spawn('pg_dump', …)` call — i.e. before any DB connection attempt — and requires the path to (1) exist, (2) be an ordinary file (not a directory, device, or symlink — even one that ultimately resolves to a valid file), (3) be readable. Any failure returns `{exitCode: 1, stderrTail: 'BACKUP_CA_ROOT_MISSING' | 'BACKUP_CA_ROOT_NOT_ORDINARY_FILE' | 'BACKUP_CA_ROOT_UNREADABLE'}` — fixed, credential-free codes, propagated by the orchestrator as `BACKUP_PG_DUMP_FAILED:…` with pg_dump never spawned, so the existing "no upload on dump failure" / "no plaintext ever written" invariants apply unchanged.
- **Ambient override resistance**: `buildPgDumpChildEnv(env, caRootPath, source)` is now the single place that constructs the `pg_dump` child env; `PGSSLROOTCERT` is always set from its own `caRootPath` parameter (defaulting to the real constant, never overridden by the CLI), never copied from `source`/`process.env`. `minimalPgChildEnv`'s allow-list (`PATH`/`HOME`/`LANG`/`LC_ALL`/`TMPDIR`/`TEMP`/`TMP`) also still does not carry `PGSSLROOTCERT` through at all, so this is enforced twice over.
- **No whole-`process.env` spread was introduced or exists anywhere in this file** — `spawnPgDump`/`spawnPgRestoreList`/the version probes all still build their child env exclusively through `minimalPgChildEnv`.
- **Unrelated child processes unchanged**: `pg_restore --list`, the `pg_dump`/`pg_restore` version probes, the Go-`age` CLI invocations, and the Docker PG18-proof helper already received no DB/R2/age/Worker secret before F8 and still do not — F8 only added `PGSSLROOTCERT` to the one child (`pg_dump`) that actually needs it.
- **Deterministic, non-flaky unreadability test**: rather than `chmod`ing a file (unreliable in CI containers that run as root, where permission bits don't block root reads), `assertCaRootUsable` takes an injectable `FsAccessChecker` (`(path, mode) => Promise<void>`) defaulting to the real `fs.access`; the test passes a fake checker that always rejects with `EACCES`, so the "unreadable" path is exercised deterministically regardless of OS/user. Production code never passes a custom checker.

Tests added (`tests/readiness/production-backup.ts`, all PASS locally — see below):
- **29 (F8-A)**: `pg_dump` child env carries `PGSSLROOTCERT === EXPECTED_PRODUCTION_CA_ROOT` alongside the existing `PGSSLMODE=verify-full`/`PGCHANNELBINDING=require`.
- **30 (F8-B)**: an ambient `PGSSLROOTCERT=/tmp/fake-attacker-cert.pem` cannot override the fixed path — checked both through `buildPgDumpChildEnv` and directly through `minimalPgChildEnv`.
- **31 (F8-C)**: a missing CA root fails closed — via `assertCaRootUsable` directly, and end-to-end through `runProductionBackup` with `PATH` pointed at a directory containing no `pg_dump` binary at all (so if the code had tried to spawn before checking the CA root, it would fail with `BACKUP_PG_DUMP_SPAWN_ERROR` instead — the test asserts the CA-specific message, proving check-before-spawn) — `uploads.length === 0`.
- **32 (F8-D)**: a directory, and separately a symlink to an otherwise-valid file, are both rejected as `BACKUP_CA_ROOT_NOT_ORDINARY_FILE`; the real file the symlink points to is accepted directly (sanity check).
- **33 (F8-E)**: an injected always-`EACCES` `FsAccessChecker` is rejected as `BACKUP_CA_ROOT_UNREADABLE`; the same file with the real checker (default) is accepted — deterministic, no `chmod`/root dependency.
- **34 (F8-F)**: `minimalPgChildEnv` excludes a fake ambient `PGSSLROOTCERT` plus fake R2/age/Worker-token secrets from the child env used by `pg_restore --list`/version probes.
