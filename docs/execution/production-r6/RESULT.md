## Scope

Add a minimal, fail-closed code path that lets `TransactionalPaymentProjection`/`PgPaymentProjection`/`PgPaymentReconciliation` admit `SQUARE_PRODUCTION`-mode bookings against a real (non-`zr_*`) Production database, **additively**, without touching any existing Sandbox/dev code path, guard, literal check, or migration. Zero live Square calls. Zero Production DB connections. Zero PR.

## What this adds

- [packages/db/migrations/0040_production_payment_admission.sql](../../../packages/db/migrations/0040_production_payment_admission.sql) — additive migration: widens `rental_bookings_mode_check` to add `'SQUARE_PRODUCTION'` (existing `SIMULATED_DEV`/`SQUARE_SANDBOX` values unaffected — the same additive-widening precedent as migration `0023`), and adds `payment_reconciliation.load_context_production`/`load_contexts_production` SQL functions, which mirror the existing `load_context`/`load_contexts` exactly except for the mode literal they read. `payment_reconciliation.dispatch`/`claim`/`finalize` were already environment-agnostic (`CHECK(environment IN ('SANDBOX','PRODUCTION'))` since migration `0026`) and needed no change.
- [packages/db/src/migration-plan.ts](../../../packages/db/src/migration-plan.ts) — registers `0040` in the canonical `migrationPlan`.
- [config/production/bootstrap-source-manifest.json](../../../config/production/bootstrap-source-manifest.json) — pins `0040`'s SHA-256, `runtimeGuards:0`, `guard:null` (it introduces no `zr_*` disposable-database guard to rewrite). `npm run test:m2b-bootstrap` confirms this does not disturb the existing 12-migration rewrite set or either migration (`0028`,`0029`) with real `runtimeGuards`.
- [packages/core/src/payment/production-projection-authority.ts](../../../packages/core/src/payment/production-projection-authority.ts) (new) — `ProductionProjectionPermit`: the converse of the existing `r15-projection-authority.ts` capability. `productionProjectionPermit(env, target)` only issues a permit when `VERCEL_ENV==='production'`, `SQUARE_ENVIRONMENT==='PRODUCTION'`, `PRODUCTION_PAYMENT_ADMISSION_AUTHORITY==='R6_PRODUCTION_ADMISSION'`, and `target.database` is a syntactically safe, non-`zr_*` identifier — all simultaneously. The permit is a `WeakMap`-issued opaque capability; `productionProjectionTarget(permit, ref)` only resolves for a booking/attempt pair matching what the permit was issued for. No ambient default: every test constructs its own self-consistent Production-shaped target, never a real hostname/database name.
- [packages/core/src/payment/payment-projection.ts](../../../packages/core/src/payment/payment-projection.ts) — `decidePaymentProjection` additively recognizes `SQUARE_PRODUCTION` as a valid mode (existing `SIMULATED_DEV`/`SQUARE_SANDBOX` handling unchanged). `verifyProjectionSource` and `TransactionalPaymentProjection` are generalized to take an `expectedEnvironment`/optional `productionPermit`, replacing 3 previously-hardcoded `'SANDBOX'`/`'SQUARE_SANDBOX'` literal checks with permit-derived expectations — default behavior (no permit passed) is byte-identical to before.
- [packages/db/src/payment-projection.ts](../../../packages/db/src/payment-projection.ts) — `PgPaymentProjection` takes an optional 4th constructor param (`productionPermit`). The DB-connection identity floor now branches: R15 target (unchanged) → Production target (new — requires the connected `current_database()`/role to exactly equal the permit's target, `<database>` and `<database>_pay_projection`) → else the original `zr_*` floor (unchanged). A Production permit against a `zr_*`-shaped database is explicitly rejected (converse-of-dev-floor), proven by mutation test (see below).
- [packages/db/src/payment-reconciliation.ts](../../../packages/db/src/payment-reconciliation.ts) — `loadBatch()`/`load()` branch to `load_contexts_production`/`load_context_production` only when `claim.environment==='PRODUCTION'`, mirroring the existing `dispatch()`/`claimBatch()` ternary pattern.
- [tests/fixtures/payment-projection.ts](../../../tests/fixtures/payment-projection.ts) — shared fixture gained a `role` field (defaults preserve every existing test's behavior).
- [tests/unit/production-payment-admission.test.ts](../../../tests/unit/production-payment-admission.test.ts) (new, 16 tests) — permit-issuance gating (all 4 conditions independently required; `zr_*`/unsafe-identifier targets rejected), `decidePaymentProjection`'s additive mode recognition, mode/environment-crossing prevention at both the core and DB layers (Production permit + wrong mode, wrong database, wrong role, wrong source environment — each independently rejected with no history write), a full correct end-to-end admission, the `NODE_ENV=production` constructor activation gate, and `PgPaymentReconciliation.load`'s environment-based SQL function selection.

## Deliberately deferred: Production `SquareWebhookConfiguration` resolver

[apps/web/src/lib/square-webhook-config.ts](../../../apps/web/src/lib/square-webhook-config.ts) resolves Sandbox webhook receiver configuration only (`VERCEL_ENV==='preview'`, `SQUARE_ENVIRONMENT==='SANDBOX'`, fixed Sandbox merchant ID), with an explicit existing comment: *"Production/future multi-environment transport is deliberately not composed in R11."* R6 does not add a Production variant. Reason: an honest Production resolver needs a real Production merchant ID, notification URL, and a `zao_square_webhook_receiver`-equivalent Production DB role/credential shape to validate against — none of which exist in this session, and none of which R6's scope (payment *admission*, not webhook *transport* activation) requires. Fabricating placeholder values for those checks would be worse than not writing the function: it would create an untested, unvalidated code path that looks activated. This is left as an explicit gap for a dedicated future change, not silently rushed in. `PAYMENT_PROJECTION_PRODUCTION_BLOCKER.md` already establishes this project's convention of keeping Production payment/webhook activation as its own dedicated, reviewed gate.
