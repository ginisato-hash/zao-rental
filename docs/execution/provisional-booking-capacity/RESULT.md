## 1. HoldService wiring — the actual "usable by a real reservation" proof

**`packages/core/src/inventory/allocation.ts`**, new export `planMixedAllocation(c, conditions, now, ignore, pin)`, used by `HoldService.command()` in place of `planAllocation` for `create`/`amend` (line ~108 of `hold-service.ts`; `availability()`'s own preview call is unchanged, still physical-only — a disclosed scope boundary, see §8):

1. Attempts the **full existing physical-only `planAllocation`**, unchanged, first. A request that is fully satisfiable physically never touches provisional capacity at all — "physical preferred" by construction, not a rule bolted on afterward.
2. Only when that is `INSUFFICIENT` are the candidate's own **eligible** requirements considered: ordinary tier (never `PREMIUM`), no `modelPromise`, exactly one requested variant, and a family the provisional pool actually covers (`SKI`/`SNOWBOARD`/`SKI_BOOT`/`SNOWBOARD_BOOT`/`WEAR_JACKET`/`WEAR_PANTS` — `POLE` is structurally never eligible, since it is not one of the six families migration 0041's own `CHECK` constraint allows into a bucket at all).
3. **Physical-preferred, per item, not just overall**: every eligible item is first excluded from the physical demand (proving the remainder is feasible without it), then **greedily re-included one at a time** — if the physical retry stays `FEASIBLE` with an item back in, that item keeps its real claim; only items that genuinely cannot be re-included stay routed to provisional. An earlier version of this pass excluded every structurally-eligible item unconditionally and was caught by its own product-path test (P3, a mixed `SKI_SET` member: physical `SKI`+`POLE`, provisional-only `SKI_BOOT`) reporting `INSUFFICIENT` when it should have reported `CREATED` — the fix (greedy re-inclusion) is what is on this branch now, not the original design.
4. **Wear items get the identical treatment through a separate, parallel mechanism**, since wear was already its own all-or-nothing quantity-pool check (`wearCapacity()`) with no per-item visibility. `packages/core/src/inventory/wear-capacity.ts` gained `wearCapacityDetailed()` — the same per-requirement work, refactored to never short-circuit on the first shortfall (a check-then-commit pass per requirement, not optimistic-mutate-then-rollback, since the `ownLoans` exclusion means a requirement's increment is 0 or 1, and a naive rollback would double-count that case) — so `planMixedAllocation` can identify exactly which wear items are physically infeasible and route only those to provisional. `wearCapacity()` itself is now a thin wrapper (`wearCapacityDetailed` + discard-on-any-failure) and is behaviorally byte-identical for every existing caller — proven by the full `test:wear`/`test:inventory` suites passing unchanged.
5. Canonical booking size for a provisional-eligible item is **read from the ledger variant itself** (`SELECT size FROM ledger_variants WHERE id=...`), never the raw request string — an eligible item whose variant cannot be resolved is not silently dropped from the demand; the fallback is refused and the original `INSUFFICIENT` stands.
6. `planAllocation` itself gained two new, strictly additive, backward-compatible parameters: `excludeKeys` (filters the candidate's own requirements before matching — every existing caller passes `undefined`, unchanged behavior) and `wearFeasible` (bypasses `planAllocation`'s own internal `wearCapacity()` call when the orchestrator has already resolved wear separately — `undefined` means "compute it exactly as before," so `availability()` and any other unmodified caller is unaffected).

`HoldService.command()` writes the result via the existing `writeAllocationClaims` (physical, unchanged) plus a new, unconditional `writeProvisionalClaims(c, target, plan.provisional, days, now)` call (matching the existing `writeWearClaims`'s own idempotent deactivate-then-reinsert shape; calling it even with an empty list is what correctly releases stale provisional claims on an amend that no longer needs them) and passes `plan.wearExcludeKeys` into `writeWearClaims` so a wear item routed to provisional is never also written to `wear_claims`.

**Disclosed simplification** (already flagged in the code's own doc comment): this is not a fully joint physical+provisional optimizer. The greedy re-inclusion order can matter when several eligible items genuinely compete for the same scarce physical unit — a scenario this pass's tests do not construct. Whenever provisional is not needed at all, the first full physical attempt already succeeds, so the common case is unaffected; this is a defensible middle ground given the alternative is a materially larger rewrite of an already-sophisticated bipartite-matching engine (`period-matching.ts`), not something this pass attempted.

## 3. Checkout/handoff gate — "Reservation allowed, physical handoff not allowed" (item E)

**`packages/core/src/payment/booking-service.ts`**:
- `verifyClaims()` (called at booking creation, payment confirmation, and — via `CustodyService` — `prepare()`/`checkout()`) now treats an `ACTIVE` `provisional_capacity_claims` row as satisfying `expectedClaimKeys()` exactly like a real `inventory_claims`/`wear_claims` row. A provisional-backed reservation is a genuine hold, not incomplete protection — this is deliberately booking/payment-scoped.
- New `verifyPhysicalHandoff(c, holdId)`: throws `PROVISIONAL_PHYSICAL_ASSIGNMENT_REQUIRED` if this hold has any still-`ACTIVE` provisional claim at all. Called from `CustodyService.prepare()` and `.checkout()` (`packages/core/src/rental/custody-service.ts`), right after `verifyClaims`, before any assignment/selection logic runs.

For the asset-backed families (`SKI`/`SNOWBOARD`/`SKI_BOOT`/`SNOWBOARD_BOOT`), `prepare()` already had a structural defense-in-depth: its own equipment-group check counts only real `inventory_claims` rows, so a provisional-only requirement would already have produced `INCOMPLETE_EQUIPMENT_GROUP` even without the new gate. The **real gap** `verifyPhysicalHandoff` closes is `WEAR_JACKET`/`WEAR_PANTS`: wear items are excluded from that equipment-group check entirely (they have no per-serial asset to select), so a provisional-only wear item would previously have reached checkout unblocked. `verifyPhysicalHandoff`'s blanket "any ACTIVE provisional claim blocks handoff" check covers both cases uniformly and gives a single, clear, purpose-built error code instead of relying on an incidental side effect of an unrelated check.

Proven end to end: P11 books and pays for a provisional-only `SKI` hold (`CONFIRMED_DEV`, proving "reservation allowed"), then asserts `CustodyService.prepare()` throws `PROVISIONAL_PHYSICAL_ASSIGNMENT_REQUIRED` (proving "physical handoff not allowed"). What this pass does **not** prove: the reverse path — a hold amended/replanned after real stock exists (via materialization, see §5) actually clearing the gate and letting checkout proceed. Building that specific end-to-end scenario needs a full amend-after-materialize product-path test this pass did not construct; the gate's own correctness (§ above) is proven, but "does staff's normal reallocation workflow actually clear it in practice" is not. Disclosed, not hidden.

## 4. Role grants — every role that now touches `provisional_capacity_*`

Wiring the module into `HoldService`/`BookingService`/`CustodyService` meant those roles now execute SQL against `provisional_capacity_claims`/`_buckets` for the first time — this pass found and fixed the resulting permission gaps **the hard way, via real-PG test failures**, not by inspection:

- **`hold`** (`scripts/application-roles.ts`, `scripts/production-app-roles.ts`): `SELECT` on `provisional_capacity_buckets`; `SELECT,INSERT,UPDATE(state,released_at)` on `provisional_capacity_claims`; `USAGE` on its identity sequence; `EXECUTE` on `provisional_capacity_effective_quantity(uuid)`.
- **`transfer`** (same two files): `SELECT,UPDATE(state,released_at)` on `provisional_capacity_claims` only — release-only, via `expireInventoryHolds`, never plans or inserts.
- **`operations`** (`scripts/operations-roles.ts`, `scripts/production-app-roles.ts`): `SELECT` on `provisional_capacity_claims` only (`verifyClaims`/`verifyPhysicalHandoff`) — no source/bucket table access at all (see §6).
- **`flow`** (`scripts/flow-roles.ts`, the role `BookingService`/`CustodyService` actually run under in every local test): `SELECT` on `provisional_capacity_claims`, guarded by a `to_regclass` presence check matching the file's existing style for tables that may not exist in an older migration snapshot.
- **`custody`** (`scripts/custody-roles.ts`): `SELECT` on `provisional_capacity_claims`, same guard style.

`provisional_capacity_effective_quantity()` (see §5) is itself `SECURITY DEFINER` specifically so that granting it `EXECUTE` does not also require granting the caller direct `SELECT` on `provisional_capacity_adjustments`/`_materializations` — the first version of this function was plain `LANGUAGE sql` and failed under the `hold` role for exactly that reason (real-PG test caught it directly: `permission denied for table provisional_capacity_adjustments`).

Production role plans (`scripts/production-app-roles.ts`) received the identical grants for `hold`/`transfer`/`operations`, for future-readiness — provisional capacity is not activated in Production today (see §11), but the role architecture is kept in lockstep with local dev, matching this repository's own established pattern (`test:m2b-bootstrap`'s `SECURITY_EQUIVALENCE` check, which passed unchanged, is exactly the mechanism that would have caught a local/Production drift here).

## 5. Migration 0041 hardening — immutability, partial materialization, evidence

Migration 0041 was corrected **in place** (not layered as 0042) — it is still local, uncommitted-to-`main`, pre-TD-review work on an iterative branch, the same pattern this repository already uses for 0040 across its own V1→V4 correction passes.

**Immutable base quantity (H)**: `provisional_capacity_buckets.quantity` is now the immutable as-registered count — no `UPDATE` grant on this column exists anywhere, for any role. A new table, `provisional_capacity_adjustments` (immutable, append-only: `bucket_id`, signed `delta`, `reason`, `actor`), is the correction ledger. `provisional_capacity_reduce_bucket(bucket_id, new_quantity)` (renamed from taking a raw `p_actor` parameter — see §6) now computes and inserts a signed delta instead of updating the row directly; the same fail-closed `PROVISIONAL_CAPACITY_BELOW_ACTIVE_CLAIMS` check as before still runs against the true current commitment.

**Partial, evidence-tied materialization (I/J)**: a new table, `provisional_capacity_materializations` (`bucket_id`, `quantity`, `real_data_acceptance_id` — a **required foreign key into the real `real_data_acceptance` table**, not an arbitrary operator claim — `actor`), replaces V1's whole-bucket-only `active=false` flip. `provisional_capacity_materialize_bucket(bucket_id, quantity, real_data_acceptance_id)`:
- Refuses a non-existent `real_data_acceptance_id` (`PROVISIONAL_MATERIALIZATION_EVIDENCE_REQUIRED`, `23503`) before any mutation.
- Accepts partial quantities: provisional 6 → real 4 leaves 2 still bookable; the bucket only fully retires (`active=false`) once cumulative materialized quantity reaches the bucket's own effective quantity.
- **Never touches `provisional_capacity_claims`** — an existing `ACTIVE` claim is neither deleted nor auto-converted. This was an explicit, deliberate design constraint (a materialization event alone must never imply a physical reallocation happened) and is proven directly: after a partial materialize call, a hold's claim is asserted still `ACTIVE`, byte-unchanged.

A real bug was caught and fixed during this pass's own testing, not merely avoided: the first implementation computed `remaining := effective_quantity(bucket) - already_materialized`, **double-subtracting** the materialized total, since `effective_quantity()` already nets it out — after the very first partial materialize call, every subsequent call (however small) was incorrectly refused. The real-PG test (`J: partial materialization`) caught this directly (`PROVISIONAL_MATERIALIZATION_EXCEEDS_QUANTITY` on a call that should have succeeded); fixed to `IF p_quantity > effective_quantity(bucket)`.

**Truthful, date-scoped availability (K)**: `provisional_capacity_available(family, age, booking_size)` — gross bucket quantity, no claims subtracted, misleadingly named "available" — is removed. `provisional_capacity_available_on(family, age, booking_size, day)` replaces it: bookable quantity (base + adjustments − materializations) **minus every other hold's `ACTIVE` claim for that exact day**, summed across every `ACTIVE`/`MAPPED` matching bucket — the same per-bucket, per-day liveness predicate the claim guard and TS planner already use. No product code called the old function (confirmed by repo-wide grep before removing it); only this module's own test file did, and it is updated. Not yet wired into any read endpoint — a disclosed follow-up, not a regression (nothing regresses, since nothing depended on the old one).

## 6. Registration security — SECURITY DEFINER, no direct table access (L)

## 9. Source B X-size resolution (item G) — investigated, not guessed

The handoff asked to investigate whether Source B's ambiguous `NNX`-token boot buckets (e.g. `26X`) could be resolved against Source A's own known models (kids `SKI_BOOT` T1/T2/T3, adult `SNOWBOARD_BOOT` FACTION RTL BOA, kids `SNOWBOARD_BOOT` PROJECT BOA/WHIPSTAR — all present with exact, already-reviewed sizes in `PROVISIONAL_CATALOG_MAPPING.csv`).

**Finding: this cannot be responsibly resolved from the data this repository actually has, and no guess was made.** `PROVISIONAL_SOURCE_B_CAPACITY.csv`'s own provenance column states plainly that Source B's own extraction already aggregated across every model within a family/age/size into one bucket — the per-model breakdown that would be needed to know *which* physical boot model each `X`-token bucket refers to was discarded before this bucket-level CSV was ever produced, and `PROVISIONAL_SOURCE_B_AUDIT.md` already documents this was deliberate ("no guess was made about whether X means .5, a JP/US/UK/mondopoint size, or something else"). Even if a plausible `X ≡ /.5` convention were assumed (matching adult `SKI_BOOT`'s Source A `22/22.5`-style pairing), Source A's own kids `SKI_BOOT` T1/T2 sizes are *unpaired* plain integers (`15`, `16`, `17`, `18`...), so a single uniform convention cannot be assumed to hold across every model without knowing which specific model each Source B bucket actually is — precisely the information that no longer exists in this bucket-level data. Activating a guess here would violate this project's own explicit "never guess" instruction for this exact source. **Disposition: unchanged from V1 — all 20 Source B boot buckets remain `BOOKING_SIZE_MAPPING_REQUIRED`.** This is a data-provenance limitation, not a code gap this pass could close.

## 13. V3 correction — review findings P1–P7

Closes the seven findings from V2's own review, on top of the same worktree (no new branch).

**P1 — `availability()` is mixed-aware.** `HoldService.availability()` now calls `planMixedAllocation` instead of physical-only `planAllocation`. Still strictly read-only: `planMixedAllocation` itself never writes (only `writeProvisionalClaims`/`writeAllocationClaims`/`writeWearClaims`, called solely from `command()`, do); `availability()`'s own transaction is unaffected. This closes the real gap V2 left open: a provisional-backed variant `command()` would genuinely accept was previously invisible to the actual Guest/Recommendation preview path (`GuestBookingService.preview → RecommendationService.preview → HoldService.availability`), which calls `availability()`, not `command()`.

**P2 — other provisional-backed holds are frozen from automatic physical replan.** `planAllocation`'s `mutable` set (the live holds another candidate's replan may automatically reshuffle) now excludes any hold with an `ACTIVE` `provisional_capacity_claims` row, via a new query scoped to the dependency-scope `nodes` already computed — the identical treatment already given to holds pinned by an in-flight transfer. A provisional-backed hold can still become physical, but only through its own explicit `amend`/`reassign` (which runs it as the *candidate*, not as another hold's automatic replan target, and so is never subject to this freeze at all — confirmed by inspection of how `ignore` excludes a self-amending hold from `nodes` in the first place, and proven directly by P12).

**P3 — exact-one protection witness.** `BookingService.verifyClaims()`'s three-way `UNION` became `UNION ALL`. `UNION` was silently folding two witnesses for the exact same `(requirement_key, day)` from different tables (e.g. a physical **and** a provisional claim for the same key/day — which should never coexist by design) into one row, making a real double-claim allocator bug indistinguishable from a single legitimate witness. With `UNION ALL`, a duplicate produces an extra row, and the existing sorted-join comparison against `expectedClaimKeys()` (exactly one entry per key) already fails closed on it — no new comparison logic was needed, only removing the table-level deduplication that was hiding the failure mode. Re-checked directly at the product-path level inside P12 (asserting the summed witness count across all three tables is exactly 1 after a reassign, not the released provisional row plus the new physical one).

**P4 — materialization is explicitly NOT ACTIVATED.** `provisional_capacity_materialize_bucket` now unconditionally `RAISE EXCEPTION 'PROVISIONAL_MATERIALIZATION_NOT_ACTIVATED'` (`ERRCODE='0A000'`) as its first statement, before touching any row — proving a `real_data_acceptance` row merely *exists* was never proof its family/age/size/quantity actually match the bucket being materialized, and the function could reduce provisional backing while `ACTIVE` provisional promises against it still existed. No runtime role (`hold`, `transfer`, `operations`, or any Production-role-plan equivalent) has ever had `EXECUTE` on this function — confirmed by grep before this correction, not merely asserted — so this guard additionally fail-closes the one remaining path: the DB owner/migration connection calling it directly. The table/function shape is preserved, unreachable by design, for a later, separately-attended physical-reconciliation phase (**`PROVISIONAL_TO_PHYSICAL_MATERIALIZATION: NOT_ACTIVATED / REQUIRES_PHYSICAL_RECONCILIATION_PHASE`** — not a PASS). Both J tests now prove the refusal fires — one with missing evidence, one with **genuine, valid** real-import evidence (the stronger proof: NOT_ACTIVATED fires before the evidence check is even reached).

## 15. V4 — 95% public capacity / staff `INVENTORY_BUFFER_OVERRIDE`, POLE conditional, X-token resolution (release-code-closure, takeover continuation)

A prior session (same worktree) had implemented the 95% public-reservation-capacity ceiling across physical/wear/provisional inventory, the explicit staff `INVENTORY_BUFFER_OVERRIDE` permission, the POLE conditional-tracking rule, and the Source B X-token (`NX=N/N.5`) resolution, but ran out of context before ever running the affected test suites. This pass picked up that exact uncommitted diff, audited it, and closed it out.

**Five confirmed, real bugs found in the uncommitted diff and fixed** (none were test artifacts — each would have shipped broken):

1. **Write-boundary recheck silently dropped `bufferOverride`.** `HoldService.command()` computed `planMixedAllocation(...,overrideReason!==undefined)` correctly at the planning step, but then called `writeProvisionalClaims(c,target,...,now)` and `writeWearClaims(c,target,...,now,plan.wearExcludeKeys)` — both missing the same flag. A legitimately planned staff-override booking would pass planning, then fail at the write-boundary recheck with a spurious `WEAR_CAPACITY_CHANGED`/`PROVISIONAL_CAPACITY_CHANGED`. Both call sites, and `writeWearClaims`'s own signature, now thread it through.
2. **`operationalTotal` counted `ledger_poles` rows as exactly 1 unit each.** A `ledger_poles` row is a quantity-pool row (its own `quantity` column, up to 1,000,000 per variant/store/status — migration 0002), unlike `ledger_assets` (always exactly one physical unit per row). The new 95%-ceiling aggregation summed `+1` per row regardless, collapsing the public ceiling for any pole-backed variant to `floor(rowCount*0.95)` instead of `floor(trueUnitCount*0.95)`. Fixed to sum `u.quantity`.
3. **`planAllocation`'s internal wear-feasibility recompute discarded its own received `bufferOverride`.** When `wearFeasible===undefined` (the normal case whenever `planMixedAllocation` had already found wear feasible), `planAllocation` re-derives wear feasibility itself via `wearCapacity(c,conditions,now,ignore)` — without passing through the `bufferOverride` parameter it had itself received. Any override-dependent wear scenario silently reverted to the strict public ceiling at this internal recompute. Fixed to thread it through.
4. **The 95% aggregate check was not scoped to the days actually being planned.** `fixedClaims` spans every currently-active claim on the relevant units, across *any* date those other holds happen to occupy — including dates having nothing to do with the current candidate or any replanned job. The original check bumped `publicUsage` for every one of those unrelated (variant, day) pairs, so one old, unrelated claim on some other date could push a completely unrelated day's request into `INSUFFICIENT`. Fixed by intersecting against `relevantDays` (the union of every job's own period in the current planning pass).
5. **`packages/auth/src/staff-input.schema.json`'s permission enum never got `INVENTORY_BUFFER_OVERRIDE` added**, so no staff account could actually be granted the new permission at all (the account-creation/update JSON schema rejected it outright). Added to both the `create` and `update` blocks.

**One additional pre-existing compatibility gap fixed** (this codebase's own established `to_regprocedure` guard convention, used throughout `scripts/*-roles.ts` for exactly this situation): `scripts/application-roles.ts`'s new unconditional `GRANT EXECUTE ON FUNCTION inventory_buffer_override_record(uuid,text)` broke every "migration-prefix" test (a pattern used throughout this test suite to verify additive migrations against a database with only an early subset of migrations applied) — since that function does not exist before migration 0042. Guarded behind the same `to_regprocedure(...)` existence check every other post-0004 grant in this file already uses.

**Test-fixing methodology**: the 95% ceiling made a large number of pre-existing tests across the whole suite fail, because they use deliberately tiny (1-20 unit) synthetic fixtures to make exact allocation/concurrency/oversell outcomes assertable — a pattern established across many prior phases (E01-E15, R-series, P-series). Each failing test was individually classified as either (a) **PUBLIC BOOKING POLICY** (an ordinary customer/guest scenario where the small quantity is incidental, not the point) — fixed by a *local*, file-scoped fixture stock top-up, never by touching the shared `seedInventory`/`seedRecommendation` base quantities other suites depend on for their own scarcity — or (b) **LOWER-LEVEL OPERATIONAL MECHANICS** (concurrency races, oversell prevention, exact-conservation/exhaustion proofs, replan/amendment races) where the scarcity is the point — fixed by explicitly threading `bufferOverride` through an authorized staff principal (every such fixture's account was granted `INVENTORY_BUFFER_OVERRIDE` explicitly; no shared helper defaults to override). `RecommendationService.preview()`/`select()`/`resume()` were extended with the same explicit, optional, audited override passthrough as `HoldService` (persisted inside the existing `recommendation_selections.selection` JSONB column — no migration needed) after confirming with the Owner that a wear-pool exhaustion/group-oversell test pair was genuinely lower-level mechanics rather than public policy, despite going through the recommendation flow.
