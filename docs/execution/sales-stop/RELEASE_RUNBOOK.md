# 日にち単位の売り止め（臨時休業）と予約一覧の受付日時 — 仕様と本番公開手順

作成：2026-11-22 JST（実装担当D、Owner依頼「日にち単位で売り止めをかけられる機能。主に臨時休業用で一括で売り止め」「予約ページで、いつ入った予約か見られるように」）。

## 1. 仕様（Ownerの選択どおり）
| 項目 | 内容 |
|---|---|
| 設定画面 | スタッフメニュー「売り止め（臨時休業）」`/staff/sales-stops`。開始日〜終了日（最長366日）と店舗（両店舗を一度に選択可）を選び、理由を入れて「売り止めにする／売り止めを解除」で一括変更。確認ダイアログあり |
| 権限 | 閲覧：在庫閲覧（INVENTORY_VIEW）。変更：在庫編集（INVENTORY_EDIT、既定でADMIN・MANAGER）。担当店舗の外は変更不可。画面の店舗選択は担当店舗だけから始まり、送信も担当店舗だけ（1店舗担当の店長が自店を設定・解除できる。PR74-UI-01） |
| 止める範囲 | 受取〜返却の期間に、受取店舗または返却店舗の売り止め日が**1日でも含まれる**予約 |
| お客様のWeb予約 | 受け付けない。日付を選んだ時点で「次の日は受付を停止しています」と表示し先へ進めない。サーバー側（HoldServiceの事前確認と確定の両方）でも `SALES_STOPPED` で拒否。さらにDB（0062の `inventory_holds` トリガー）が、アプリの版に関係なくお客様の仮押さえを拒否する（§4） |
| スタッフの新規予約 | 警告を表示し、「売り止め日と承知のうえで予約を作成する」にチェックした場合だけ進める（サーバーは拒否しない） |
| 既存の予約 | 変更・取消しない。設定画面に「売り止め日にかかっている既存の予約」として一覧表示（下書き・取消・完了・返却済・不受取は除く）。**予約閲覧（BOOKING_VIEW）がある人だけ**に表示し、無い人には「予約の表示には予約閲覧の権限が必要です」と出す（「0件」とは出さない。読み取り中に権限が外れた場合は応答しない。PR74-AUTH-01）。全件数を表示し、100件ずつ「前へ／次へ」で最後まで確認できる（PR74-UI-02） |
| 記録 | すべての設定・解除を変更履歴に残す（追記のみ、変更・削除不可）。売り止め行も更新不可（解除＝削除＋履歴） |
| 公開側に出す情報 | 店舗と日付のみ（理由・担当者は出さない） |
| 予約一覧 | 「受付日時」（JST）列を追加。予約詳細にも表示。CSVでは「受付日時（JST）」（`YYYY-MM-DD HH:mm`）を**すべての既存列の後ろ**に付ける（「不足あり」CSVでは「不足判定」の後ろ。既存の列位置は変えない。PR74-CSV-01） |

## 2. DB変更 0062（`packages/db/migrations/0062_store_sales_stops.sql`）
- 新しい表2つ（`store_sales_stops`、`store_sales_stop_history`）と関数2つ。既存の表・行は変更しない。
- 書き込みは `store_sales_stop_set()`（SECURITY DEFINER、操作者は認証済みの `zao.actor`）だけ。アプリは先に INVENTORY_EDIT と店舗を `ops_assert_actor` で確認する。
- `store_sales_stopped_days()` だけを PUBLIC 実行可（店舗＋日付のみ返す）。予約画面と予約受付判定が使う。
- 0062未適用のDBでは売り止め判定は「なし」として動く（新しい版を先に配信しても従来どおり）。
- `store_sales_stop_hold_guard`（`inventory_holds` のBEFORE INSERT/UPDATEトリガー）：持ち主がGUESTの有効な仮押さえについて、期間か店舗が売り止め日にかかる新規作成・変更を `P0062` で拒否する。新しい版はこれを `SALES_STOPPED`(409) として扱う。支払いの初回開始（仮押さえの決済状態が「未払い／失敗」から「支払い中」に変わる更新）も同じ判定にかける。このため、売り止め前に作った未払いの仮予約も、売り止め後には支払いを始められない（決済事業者は呼ばれず、何もcommitされない。PR74-ROLLBACK-01）。スタッフの仮押さえ、売り止め前に始まった支払いの照合・完了、期間・店舗が変わらないその他の更新（期限など）は対象外。0062より前のアプリの版でも、お客様が売り止め日を予約することはできない。
- `npm run production:verify-sales-stop`：本番DBをREAD ONLYで読み、0001〜0062の登録、所有者、3つのガードトリガーが有効なこと、権限、今日以降の売り止め日の件数を返す。書き込みは0。トリガーは通常のセッションで発火する状態（`tgenabled` が O か A）だけを有効とし、replica専用（R）と無効（D）は拒否する（PR74-VERIFY-01）。COMMITの結果が不明な場合の読み戻しと、切戻しの判断に使う。

## 3. 本番公開の順序（PR #73 と同じ安全手順）
1. PRの自然CI SUCCESS と ChatGPT TD の独立レビュー（B/H/M 0）→ 通常のsquash merge。
2. **Owner**：merge後の最新バックアップで復元試験（**61本の登録**、`expectedMigrations: 61`）。age秘密鍵は非表示入力のみ。
3. 実装担当：`npm run production:restore-evidence-finalize-pre-0062`（記録 `restore-pass-pre-0062.json`、24時間有効）。
4. `npm run production:install-sales-stop-migration` → `npm run production:install-sales-stop-grants`（どちらも pre-0062 の復元記録・accepted main・verify-full TLS が前提。再実行は拒否、COMMIT後は読み戻しのみ）。
5. 公開許可（`PRODUCTION_RELEASE_ID`/`PRODUCTION_PUBLICATION_APPROVAL`）を、受け入れ済みの新しいmainに結び直す。Issue #47の既存の包括GO（工程7）と `release-code-closure/PUBLICATION_HANDOFF.md` のとおりで、**通常の公開GOを取り直さない**。`releaseId` は受け入れ済みの新しいmainのSHAにし、`origin`・`approvedBy`、Ownerの元の承認時刻 `approvedAt` は既存の正式記録のまま。古いreleaseIdの流用や、新しい承認時刻の作成はしない。新しいOwner制限や、実際の自動承認拒否があった場合だけ止まって確認する。→ 同一artifactを公開ドメインに付けずに配信 → 2回の確認 → promote。
   - 実Productionの復元試験でage秘密鍵を入力する工程だけは、従来どおりOwner本人が行う（手順2）。
6. 公開後：売り止め画面の表示（本番では試験用の売り止めを1日入れて解除するかはOwner判断）、予約一覧の受付日時、公開予約画面。

## 4. 戻し方（PR74-ROLLBACK-01）
**原則：旧版に戻しても、休業日のWeb予約を再び受け付けてはならない。** 0062は売り止めをDBでも強制する（§2のガードトリガー）。このため、売り止めを知らない旧版（例：PR #73の `dpl_CimMFoXFmQxch8tqy7yHN5bQ1df8`、main `abdc1ed`）に戻しても、お客様の仮押さえは売り止め日にかかる時点でDBが拒否する。旧版では理由の表示はなく、一般的なエラーになる。売り止め日にかからない日の予約は通常どおり受け付ける。

配信を戻す場合の手順：
1. **戻す前：** `npm run production:verify-sales-stop` を実行し、`PRODUCTION_SALES_STOP_VERIFIED` と `guestHoldGuard: ENABLED` を確認する。今日以降の売り止め件数も控える（読み取りのみ。accepted mainのcheckoutから実行する）。
2. 結果が `VERIFIED` でない場合（トリガーが無効・欠落している、権限が違う、など）は、**旧版へは戻さない**。新しい版のまま修正して再公開する。原因が分かるまで売り止めの解除もしない。
3. 戻す先は、正式domainに過去に付いていた既存のimmutable deploymentに限る。Vercelの通常のpromote（`vercel promote`）で切り替える。project envを変えただけで旧deploymentに反映されたとは見なさない（envは各deploymentに固定されている）。保護の解除や新しいCLIの操作手順は作らない。
4. **戻した後：**
   - もう一度 `production:verify-sales-stop` で `ENABLED` を確認する。
   - 正式domainの `/api/readiness` を確認する。`/api/health` の `bookingAvailable:false` は稼働確認用の固定値なので、受付停止の証拠には使わない。
   - 公開予約画面で、売り止めがない日付の候補表示ができることを確認する（予約・決済は行わない）。
   - 売り止め日の仮押さえ拒否は、DBの試験（`test:sales-stop` のROLLBACK-01、`production-0057-owner-apply` のトリガー無効時の拒否）で証明済み。本番で実際に仮押さえを作って試すことはしない。
5. 売り止めの画面と、売り止め日の表示は旧版にはない。売り止めを設定・解除する必要が出たら、新しい版へ戻してから行う。旧版の期間中は、スタッフは新規の売り止めを設定できない。既存の売り止めは引き続きDBで効いている。
6. DBは戻さない。0062は追加のみで、既存の予約・在庫・売り止め記録・履歴はそのまま残す。

- 公開承認envを外しただけでは、受付停止の証拠にならない。
- 既存のR3 dark profile（`flags.booking=false`）は、新規予約だけでなく決済・予約の確認／復旧・スタッフ新規予約もまとめて止める。そのうえ新しいdeploymentとstageが必要になる。このため、通常の切戻しには使わない。上の1〜2でDBの防御が確認できない場合の最後の手段で、使うときはOwnerの判断とする。
