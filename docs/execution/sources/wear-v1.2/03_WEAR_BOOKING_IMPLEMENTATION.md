# ウェア事前予約：推奨実装契約
Version 1.2 / 開発用設計 / 新しい運用判断は本文に提案と明記

## 1. 採用する形
**売る単位は上下セット、管理する単位はジャケット1着・パンツ1着の個別Asset、予約時はサイズ条件の柔軟な仮割当。** 道具セットは販売上の組合せで、専用の別在庫を持たない。上下単独販売（衣類のみ予約）はP0、ジャケットだけ/パンツだけの小売メニューはP1。ワンピース/つなぎ実在品が来たらJACKET+PANTSに捏造変換せず別構成としてpending。

### 比較
|方式|長所|短所|判断|
|---|---|---|---|
|上下ペア1Asset|受渡し1スキャン、簡単|上M/下L、片側洗浄や紛失の追跡困難|本当に固定ペア運用を選ぶ場合のみ候補|
|部位/サイズ/店舗の数量在庫|登録・受渡しが最速|混在返却から誰のものか逆引き不可、洗浄/補修履歴が個別に残らない|ポールには適するが衣類の今回要件では次善|
|上下別個体+販売bundle|サイズ交換、片側返却、洗浄、店舗移動が追える|タグ貼付・通常2スキャンが必要|既存の連続返却モードを生かせるため推奨|
Booqableの個体/数量、TWICEの構成品bundle、Rentmanのphysical/virtual distinctionを比較した設計判断。どこかのソフトと同一実装と称さない。[T01,T02,T05,T06]

スキー/両種ブーツの左右1組1Assetとは別契約。衣類の上下に同じIDを貼って一方だけで全返却にしない。ユーザーの既存左右仕様を衣類へ無断で拡張しない。

## 2. 200着を予約数へ直結させない
既知なのは約200着の計画。上下セット200組か、総パーツ200点かは未確認。
- 200上下セットなら理論上ジャケット200/パンツ200、個体約400点。
- 合計200点なら上下数が均等でも最大100組、サイズ適合でさらに減る。
- 店舗・サイズ・外観組合せ・清掃/整備・将来予約の条件を通した数だけ予約可能。
最初はsource_unit=UNKNOWNでstagingし、実際の在庫表と受領で確定する。新規Asset数や成人/子供比率を捏造しない。

## 3. データの責務
既存model/variant/Assetを再利用。追加する論理属性はgarment_kind(JACKET/PANTS)、メーカー/モデル版、原サイズ表示、サイズ規格/fit/cut、該当実寸と出典、使用競技、年齢適格性、店舗/棚、清掃状態、予定/実ready時刻、ケアプロファイル、既存QR。familyをWEARのままgarment_kindに分けるか、既存enumを安全に拡張するかは現コードで決定。
衣類はSKI/SNOWBOARD二重登録しない。両方に使えるものは共有物理プール、専用品はcompatible_sportsで制約。衣類のクラスはSTANDARDを基本にし、道具Premiumだから衣類もPremium必須という共通tier誤結合を作らない。
価格表示のwear_set_line、bundle_adjustment、個別fulfillment requirementsとasset assignmentを分離。価格用上下セットと各衣類を両方請求しない。料金を各パーツへ配分する場合も内部配賦であり、上下別販売額を意味しない。

## 4. 顧客画面
最初に利用者ごと『道具のみ／道具＋ウェア／ウェアのみ』。衣類のみの人にスキー長・足サイズ・DIN入力を要求しない。スキー/ボード混在、衣類の有無混在を許す。
道具SETカードの横に『ウェア上下を追加 +4,000円/今回1日（単独5,000円）』等、選択期間の実総額を表示。未選択を既定ONにしない。フルセットという語だけで手袋/帽子/ゴーグルまで含まれる誤認を作らない。無料ヘルメットは既存方針の適格条件・在庫確認を別に表示し、ウェア価格に勝手に含めて提供保証しない。
ジャケットとパンツを別々にサイズ選択（M/L混在可）。身長は既存入力から再利用。必要に応じ普段の上/下サイズ、任意のウエスト等を案内するが、メーカー実サイズ表の根拠がない一律自動換算を作らない。年齢判定とサイズ適合は別。ボードに体重・レベルの必須入力を再導入しない。
写真はプランイメージと現物モデル指定を分ける。ウェアは初期に色柄・モデル非確約、サイズ/部位/適格性のみ保証。スキー/ボードのPremiumはモデル指定。ウェアに現物写真がなくても非公開placeholderと説明下書きは進めるが別モデルの写真を現物扱いで公開しない。
プロフィールと規約確認を完了してから全員全構成品HOLDを開始。入力の初めから600秒を消費しない。1着不足でも選択グループを無断で部分確保しない。『衣類を外して続行』はユーザーの明示操作と新しい見積/在庫確認が必要。

## 5. 在庫・HOLD・同時処理
最終グループHOLDは板・ブーツ・ポール・ジャケット・パンツを同一の成立判定/DB取引で全期間確保。可能な在庫は毎日入れ替わってよいというdaily countにしない。上下の適合条件（必要ならstyle/pairing group）を満たす組合せを探す。
同じ衣類をウェア単独と道具セットの2予約に同時に貸さない。soft assignmentは同じ約束を満たす個体だけ組替え、準備済み/貸出済みを自動変更しない。故障や汚損発見は将来予約への影響を提示して明示変更へ。
旧APIは1人最大3用品・familyに衣類なし。新規はスキー最大5用品、ボード4用品。members20を維持し、候補数、UTF-8最大要求、料金line数、quote hash、solver scope、ロック順、許容payload、DB制約、監査とテストの一式を更新。global body上限を無制限にしない。
既存のpricing.productKeyは1人1商品と固定18keyを前提としている。participantとcommercial linesを分離し、衣類を後から金額だけ足す迂回を作らない。pricebookを別namespaceで拡張して既存216値を保持。runtime validateTable/productKey/coupon eligible mappingも含めて整合させる。
追加データはmigrationで既存レコードを破壊せず、過去見積/支払のsnapshotは旧schema版のまま再現する。

## 6. 清掃と返却
受領→検品待ち→必要な洗浄/乾燥/補修→ready。返却ボタンだけでAVAILABLEへ戻さない。洗濯条件は現物ケアラベルとメーカー資料に従う。全素材を同じ高温処理・所要時間と仮定しない。[T03,T04,T08,T09]
将来予約は返却予定＋版付きturnaround計画/清掃拠点と移動時間で見積もる。一方、今日の実貸出には実際のready確認が必要。計画時刻が来たことを実洗浄完了と扱わない。
本番のturnaround値は未計測なのでnullの公開ゲート。テストでは専用値（例12h/24h）を明示注入し、それを本番defaultにしない。数値未確定でもモデル/API/UI/反例は作る。すべての将来予約を洗浄完了するまで無期限禁止にはせず、検証済み計画と実readyを区別する。
turnaroundポリシー変更で既存予約を黙って消さない。影響一覧/再割当/要対応を記録し、保護中個体が新予約へ二重開放されない。洗浄予約・移動予約・顧客予約を混ぜない。
スタッフ返却モードでジャケット/パンツを混在連続スキャンし、それぞれloan cycleを特定。同じ個体を再読・別端末送信しても二重返却なし。ジャケットのみ戻ったらpants未返却。店違い返却は実所在地を更新、洗浄計画を再評価し、受領事実を拒否しない。履歴と現物IDは不変。
サイズ交換は実際の在庫を再確認して原子的に切替、旧割当保持→新割当成立後のみ解除。試着段階の交換と使用後交換を分離。使用済み旧衣類はdirty、追加で2着貸したことにせず返却/交換履歴へ。現行一周委任で商品変更/追加返金が未承認なら、その金銭処理だけ後続に残す。

## 7. タグ・運用速度
ジャケット/パンツそれぞれの内側ケアラベル付近などへ、人が読める短い個体codeとQR。防水膜へ穴を開けたり、洗濯条件に合わない接着材を一律採用しない。縫付け/熱転写/既存ラベル利用の採否は現物と洗浄試験後。今はQR出力・一括紐付け・手入力fallbackを実装し、新しいプリンター/RFID購入は要求しない。
現物のブランド説明を1着ずつ入力せず、model/variant単位の内容を共有、数量から個体IDを一括発行。QR再発行は同じAsset ID。20人の返却で予約を20回開かなくても現物から逆引きする。

## 8. プライバシーと権限
guest contextはstaffアカウントを偽造せず所有を確認。実寸/写真等は公開URL/分析イベント/ログに出さない。管理の台帳/衣類状態/import/media/price/release権限は分離、CASと書込み直前の失効反映を維持。CSV/macro/式、任意URL、未検査画像を実行/公開しない。
本番DB/実在庫/実Square/外部storage/新規有料サービスは別承認。清掃ジョブは業務処理であり、保留Runnerを有効化する口実にしない。商品原本や受領表・仕入情報をpublic repoへ入れない。
