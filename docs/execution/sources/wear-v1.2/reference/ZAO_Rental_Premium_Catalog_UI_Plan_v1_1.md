## 0.1 v1.1：年式別保持と最小入力の契約

### 対象シーズンの明示前提
ユーザーの「過去2シーズン」は個別年式を指定していない。本追補では2026/27の入荷準備を基準に、2025/26・2024/25を過去2季と解釈する。既に参照された2026/27は新シーズン用の別枠として保持する。したがって収集計画は新季＋過去2季の3季分であり、「ユーザーが3季と明示した」とは記録しない。個別年式の訂正があればその指定を優先し、先に収集した根拠を破棄しない。

カタログの掲載シーズン、製品仕様の版、現物の製造年、当店の入荷年は別の情報とする。年式不明の現物を、入荷年や最新カタログへ自動対応させない。次季になっても、現物・予約履歴が参照する旧商品情報は消さない。

### 受け取る最小入力
| 情報源 | 最低限想定する内容 | 必須としない追加情報 |
|---|---|---|
| サロモン | 原表のモデル名、入荷数量、2拠点に関する原表上の記載 | SKU、年式、長さ、色、シリアル、商品説明、画像 |
| ChatGPTの調査 | シーズン・カテゴリー別の公式商品リスト、仕様、出典、確認状態 | 資料に存在しない項目を埋めた完全表 |
| オーナー | スキー現物の写真 | 全個体分の説明・仕様の入力、全関連商品の写真 |

店舗別内訳があれば保持する。2拠点合計しかない場合は未配分数量として保存し、勝手に半分ずつ配分しない。数量単位が原表にない場合は、スキー2本＝1ペア等の既存運用単位と原表の意味を照合し、不明なら数量展開だけを止める。

モデル名＋数量だけで取込受付を拒否しない。原文と数量を取り込んで候補照合・説明の下書きまで進める。名称一致だけで確定製品版・長さが決まったとは扱わない。例えば同名モデルが2季あり、複数の長さがある場合、カタログ内の候補のうちどれが到着するかは原表だけでは確定しない。

### 例外だけ確認する
1. 原表モデル名を保持し、正規化名・別名から候補を列挙する。
2. 任意のSKU・年式・長さが付記されていれば追加根拠として利用する。
3. 未一致・複数一致だけを要確認一覧へ分離する。公式表の候補が1件というだけで、収集済み範囲外の製品がないとは断定しない。
4. 必要なものだけ現物の型番・長さ表記、納品ラベル、オーナーの写真と照合する。図柄の類似やAIの自信だけで年式を確定しない。
5. 確定までの行は取込行／入荷予定の下書きとして保持し、予約可能なvariantや確定入庫数へ展開しない。任意の説明項目の不足ならその項目だけ省き、他の作業は進める。
6. 同じ確定モデル版・サイズ・仕様の繰返しは保存した対応を再利用する。ただし将来届く同名品まで無条件に同じ年式だと扱わない。

プレミアムの予約公開に必要なのは、選択したモデル版・当店取扱長さ・履行可能な現物の対応である。モデル情報の収集完了と、入荷品の識別完了は別ゲート。

### 写真の扱い
掲載用のスキー写真はオーナー提供を基本にする。同じモデル版・同じ外観で共用できる商品写真を、個体台数分撮らせない。異なる図柄・年式・構成を同じ写真で無断代用しない。
型番・長さ刻印の写真を確認用として追加できると、入荷行の曖昧さを解く助けになる。ただし掲載用代表写真1点は、納品全数がその長さである証明にはしない。写真の提供者・用途・同意を保存する。
スノーボードやブーツ等の写真供給は今回確定していない。オーナーの担当を勝手に拡大せず、写真未手配として下書きを進める。写真未着を理由に商品仕様・取込基盤の処理全体を止めない。

### 調査成果の形式と完成判定
- 年式別商品リスト：model identity、名称・別名、カテゴリー、掲載シーズン、資料の所在。
- サイズ別仕様：variant、長さ／サイズ、該当サイズに紐づく数値、単位、出典。未掲載値はnullと理由。
- 根拠台帳：source URL／資料版／ページ・位置／確認日時／確認状態。画像・表の対応は必要箇所を実際に確認する。
- 説明下書き：検証済み事実だけを根拠とするJA/EN。資料原文の大量転載や不明性能の創作をしない。
- 網羅性台帳：season × categoryごとに、入口確認／本文取得／商品抽出／照合済み／取得不能を分ける。件数は抽出後に実数を数える。

収集対象はアルペンスキー・スノーボードの板、両種ブーツ、ビンディング、ポールを優先し、公式各季カタログに載るヘルメット・ゴーグル・プロテクター・関連用品も資料範囲内で索引化する。索引を持つことはその商品を当店のレンタル対象へ追加することではない。公式未掲載のレンタル専用品・地域別仕様は「未掲載／未確認」として分離し、似た市販品で埋めない。

**本追補作成時点では、公式の対象年式入口と一部カテゴリーリンクを確認した段階。全商品の抽出・仕様照合・内部DBへの投入は未完了。**

## 2. プレミアムの商用契約［PREM-01］

### 2.1 プラン別の方針

|プラン|予約時に約束する内容|内部の個体再割当|
|---|---|---|
|Regular|既存の競技・年齢・クラス・選択サイズ等。モデル非確約|同じ約束を満たす個体に限定して可能|
|Premium|選択モデルの識別可能な版・仕様＋選択した実在長さ＋既存の商品条件|同じモデル版・長さ・約束した仕様の別Assetだけ可能|

モデル名だけを識別子にしない。ブランド、メーカーの識別コード、製品版・年式、構成仕様の一致を管理する。同じメーカー品番が継続モデルに使われる場合は、年式を含む公式の同一性根拠を残す。単に同名だから同一、または季節が違うから必ず別仕様、と自動決定しない。

モデルごとに長さが1種類だけなら、実在する長さを明示し、無いサイズ選択肢を作らない。同条件の現物が1点だけなら、それを全期間保護する結果になる。物理Assetを顧客へ公開する必要はない。

### 2.2 全経路で保持する

選択内容に、サーバーが検証可能な model identity/revision と variant identity を含める。実フィールド名は既存の命名に合わせる。

推薦 → 全員分HOLD → 見積 → 予約・決済attempt → 確定snapshot → 準備／貸出照合 の各段階で同じ商用条件を確認する。

- ユーザー入力のmodelIdとvariantIdの関係をサーバーが再検証する。
- 別モデル・別長さへの自動代替、PremiumからRegularへの無断変更は禁止。
- 売切れ・故障時は、別モデルの提案を表示できるが、選び直しと再評価なしに予約内容を変えない。
- 同じPremiumでも、全員分のブーツ・ポールが成立しなければグループHOLDは成功しない。
- ブーツ・ポールまでメーカー特定モデルを保証するとは解釈しない。共通在庫をPremiumへ使う可否も既存の構成品契約に従い、新しいtier横断を勝手に追加しない。
- 身長−20cm±15cm、年齢境界、ブーツ＋1cm等の既存ルールを、この変更だけで解除しない。Premiumの別適合ルールが必要なら別の営業・安全判断として提示する。
- 外側の候補一覧では別モデル比較を可能にするが、短め／長めボタンでモデルを黙って変更しない。
- 既存のモデル非確約HOLD・見積・予約は、後からモデル確約済みへ書き換えない。新ポリシーを版付きで適用し、移行対象を明示する。

### 2.3 UIへの反映

Premiumは「モデルカード → 当店が実際に取り扱う長さ → 日程・店舗条件での空き確認」を基本とする。日程が先に決まっていれば、用意可能なモデルへ絞り込む。モデルを先に見た利用者も同じ予約contextへ合流させる。

カードにはモデル名、該当版・長さ、根拠付きの用途説明、許可された対応写真、選択期間の総額、用意できるかの状態を表示する。日程未確認で「残り1」と表示しない。

PremiumへRegular向けの「写真は取扱例、モデル指定不可」を一律表示しない。逆に同じ写真を使ってRegularにも特定モデルを保証したように見せない。

## 3. 情報源と正確性の設計

### 3.1 役割別の正本

|情報|優先する出所|出所だけでは証明できないもの|
|---|---|---|
|当店へ何を何個届けるか|当店向け出荷・納品資料|実際の受領、破損なし、貸出準備完了|
|当店に何が実在するか|受領記録、現物ラベル・シリアル、棚卸|メーカー説明の正確性|
|モデル・サイズ別の公式仕様|メーカー商品マスター、該当版の正式資料、正規商品ページ|当店在庫数・自店レンタル価格|
|写真・文章の掲載範囲|提供素材と使用許諾・権利記録|全用途の無条件な二次利用|
|公開の説明|根拠に紐づけた承認済みcontent revision|実在しない性能や適合の保証|

メーカーの販売可能在庫一覧は、当店の入庫一覧とは別。入力モードを少なくとも SUPPLIER_AVAILABILITY / EXPECTED_DELIVERY / RECEIVED_DELIVERY / SHOP_STOCK_SNAPSHOT として区別できるようにする。名称は実装提案であり既存状態に無理に追加しない。

### 3.2 指定URLの扱い

- 8948は2026/2027アルペンスキーの特設ページ。SKI / BINDING / BOOTS等の公式PDFへの入口。
- 4834は2025/26スキーの特設ページ。同じ年式資料ではない。
- 3333は2024/25スキーの公式カタログ案内ページ。
- スノーボードの公式カタログページには2024/25・2025/26・2026/27の区分がある。スキー資料からボードの仕様を補わない。

今回、入口とリンク構造を確認した。2026/27スキーPDFの解析テキストも確認できたが、PDF表画像の照合は取得上の問題で未完了。2025/26のPDF本文の全件読解も未完了。両年の全SKU・全長さを検証済みデータとして提供したものではない。サロモンからの新しい実在庫表はまだ受領していない。

### 3.3 「完全に間違いなし」の扱い

Web収集やAI抽出だけで、外部資料の誤記・別年式・未掲載・現物相違までゼロと保証しない。システムが保証すべきなのは、検証状態と根拠を区別し、必要な証拠が不足する事実を確定データとして流さないこと。

各事実に、source document / URL / content hash / 取得日時 / シート・セルまたはページと位置 / 原文値 / 正規化値 / 単位 / 対象モデル版・長さ / 検証状態 / 確認経路を持つ。

- 同一SKUの一意対応、商品種別、長さ、年式・仕様、数量単位などの必須条件を検査する。
- SKUの部分一致、似た名称、生成AIの自信度だけで確定しない。
- 資料の繰返しコピーや同じ原本を参照する2モデルの一致は、独立した事実証明と扱わない。
- ペア重量／1本重量、長さ単位、ビンディング同梱／別売、製品全体／構成品コードを混同しない。
- 同じモデルの長さ違いの数値を流用しない。必須の表対応は原ページで確認する。
- 事実が矛盾した場合は候補と出所を両方保持し、公開値を自動決定しない。
- 任意の説明項目が不明ならその項目を省略して下書きを進める。必須の識別・数量が不明な行だけを隔離する。

## 4. データモデルの分離［CAT-01］

既存表へ追加境界として接続し、並行する別の在庫エンジンを作らない。

1. **Model identity/revision**: 製品の共通情報。メーカー、製品種別、正式名称、コード体系、版・シーズン関係、用途・技術情報の根拠。
2. **Variant**: 長さ・サイズ・幅・構成等。SKU/JAN/EAN、長さ依存の仕様、対応するmodel revision。
3. **Equipment Asset**: 実物ごとの不変ID、対象variant、入庫・所在地・状態・履歴。スキー・両種ブーツは左右1組＝1個体。ポールは既存ペア数量。
4. **Rental offering / commercial policy**: セット・単品等の販売単位、既存料金key、年齢・tier・モデル保証方針。メーカー定価と分離。
5. **Content revision / media binding**: ja/en説明、短い用途、特徴、注意点、画像・権利、公開release。1モデルの説明を全個体分複製しない。
6. **Source/import job**: 原本、列mapping版、照合候補、変換、差分計画、commit、個体生成対応表、監査・例外queue。

JAN/EAN/GTINは商品識別であり、その同一商品を複数所有した際の個体番号とは分ける。同一商品の2ペアへ別々のAsset IDを発行する。既に現場QRがあるAssetは再インポートでID変更しない。

## 5. メーカー一覧からの処理［CAT-02］

### 5.1 初回設定と通常運用

メーカー原本をそのままアップロードし、列対応・資料の意味・数量単位をテンプレート化する。以後、同じ様式なら同じ変換を使う。毎回メーカー資料に合わせてコードを書き直すのではなく、データ処理として実装する。

推奨順序:
原本の非公開保存 → 様式と意味の識別 → 列mapping → SKU/長さ/数量等の正規化 → 既存モデルと照合 → 必要な公式情報を補完 → 下書きと差分計画 → 正常・要確認の分離 → 明示一括反映 → 受領／現物確認 → 公開release。

初回はxlsx/CSVの通常表を優先する。PDFしかない資料はページ・表対応を確認し、壊れた抽出をそのまま使わない。マクロ、外部参照、数式を実行しない。Excelで入力した数値により消えたJAN先頭0等を推測で復元しない。

### 5.2 自動登録の単位

例示のMODEL-Aを15ペアと20ペアの2行で受け取った場合:
- 同じ版・仕様のmodel共通情報は1件。
- 長さが異なればvariantは2件。
- 数量が当店受領数と確定した場合、Asset計35件の生成計画。
- 説明は共通部分1件とサイズ別データ。35ページの手作業は不要。

出荷予定の段階では入荷予定／受領待ちであり、AVAILABLEにはしない。予定数量を根拠に物理Assetを先行発番する設計でも、未受領を明確にし、実在・準備済みと扱わない。

### 5.3 再投入・改訂

原本hashは完全同一ファイルの検知に使うが、それだけでは不十分。
- 行順の変更・別名保存・改訂版を同じ入荷の追加納品と誤認しない。
- 納品/注文番号・明細ID・資料版・照合済みmodel/variant等から安定した取込対象を管理する。
- 安定IDのない同一商品複数行は、曖昧なまま全行を別商品へ展開しない。初回に対応を解決し、そのmappingを保存する。
- 数量増加は差分計画、数量減少は棚卸・訂正計画とし、既存Asset・QR・貸出・HOLDを自動削除しない。
- 空欄や一覧からの欠落を、退役・削除の命令にしない。
- 公開説明、スタッフ修正、所在地を、メーカーの次回一覧で自動上書きしない。

### 5.4 手作業を例外に限定する

一致したものの下書きは継続生成し、曖昧な行・矛盾・素材権利の不足だけを要確認queueへ残す。正しいデータを毎台確認させず、件数と合計、対象差分を一括で確認する。

AI抽出候補と確定済みカタログを別管理する。原本照合と必要条件に合格した項目だけを反映できる設計にする。一括下書きに部分成功を許す場合はPARTIALと明示し、公開releaseは選択した対象全体で成功／失敗を決める。

## 6. 説明・画像の生成［CAT-03 / CMS］

モデル・版ごとに、検証済み事実から公開コンテンツの下書きを作る。テンプレートを使えば、モデルごとに新しい画面コードを書かずに一覧・詳細へ反映できる。

下書き内容:
- 正式モデル名・版、当店取扱長さ。
- 原資料に根拠がある用途・特長を短く整理。
- 正確に照合できた長さ別仕様。
- セット内訳、店頭試着・最終調整、Premiumのモデル指定条件。
- 出所に紐付くJA/EN原稿。重要条件の翻訳検査。

AIに許すのは、情報の候補抽出と根拠付きの表現案。資料にない性能、安全性、利用レベル、優劣、人気、在庫、保証を補完しない。全文章の自由生成より、構造化事実＋限定テンプレートを先に用意する。

写真はメーカーから利用許諾付き素材を受け取るか、許可された現物写真を使用する。近い年式・似たモデルの写真で代用しない。許諾なしのWeb画像を取り込んで本番公開しない。権利未確認は画像の公開だけを止め、カタログ下書きまで全部停止しない。

既存UI仕様のBULK-01は既存offerの説明更新。今回のメーカー取込は商用mappingやAsset生成を伴う別機能であり、説明CSVに価格・在庫・新商品作成権限を混ぜない。

予約画面の要求中にWeb収集や生成AIを呼ばない。外部情報の取得は管理用ジョブで行い、顧客には検証済み内部データと現在の在庫判定だけを返す。外部サイトが停止しても既存公開catalogは読み出せるようにする。

## 7. セキュリティと運用

- 取得先はメーカーから提供された資料／公式ページと確認済みリンク先に限定。任意URL入力や全Web検索の上位を真実としない。
- URL取得を設ける場合はドメイン・パス・redirect・解決先IPを検査し、内部ネットワークや資格情報へ到達させない。
- 取得資料中の命令、添付macro、外部リンクを実行指示と扱わない。
- jobの実行者・権限・対象版を保存し、再開時・反映時の権限剥奪とCASを確認する。
- 外部収集失敗と資料未一致を区別し、少数回の再試行上限を設ける。残件は保存し、他の正常行を継続する。
- 原本、仕入単価、納品先・取引情報、未公開素材は非公開で扱う。公開GitHubへcommitしない。
- 既存Teamレビューのコード資料送信承認を、メーカーの非公開原本の外部送信承認と読み替えない。
- SaaS契約・モデルAPI課金・storage・外部送信が新たに必要なら、その操作だけ別判断に分離する。
- AI開発Runnerと業務用import/media jobは別。保留中Runnerを起動しない。

既存委任の時間・レビュー予算は自動で増やさない。UIの承認・Premium方針を現在のスコープへ記録し、カタログ基盤を別のまとまった実装範囲として承認する場合も、細かな項目ごとの人間中継を再導入しない。

## 9. 受け入れ条件

1. 同名・別年式／仕様の製品を無断で統合せず、SKUと年式の根拠を保持する。
2. 型番が曖昧な行だけが要確認になり、他の正常行の下書きは生成される。
3. メーカーの販売可能数を当店在庫に加算せず、出荷予定は受領待ちになる。
4. 1モデル2長さ・複数数量を、共通model＋variant＋必要数のAsset計画に展開できる。
5. 同じ原本の再投入、別名保存、行並替えでAsset・QRが二重発行されない。
6. 改訂の数量減で現物・貸出履歴・既存HOLDを自動削除しない。
7. 1点しかないPremiumの同一モデル／長さへ同時に要求した場合、全期間で成功は1件のみ。
8. 別モデルしか空いていない場合に、同じ長さという理由だけで無断確保しない。
9. PremiumとRegularの混在グループで、ブーツ／ポールまで全員分が成立したときだけHOLD成功。
10. モデル／variantの改ざん、不一致、年齢・クラス違反を通常APIで拒否する。
11. 売切れ後の選び直し失敗で、元の有効HOLDが消えず、変更でTTLが延びない。
12. 商品説明の改訂で、既存の予約・見積のモデル約束と金額が書き換わらない。
13. 同一modelの多数Assetで説明・画像bindingを重複作成せず、一括更新が反映される。
14. 値・単位・年式が矛盾した抽出結果を確定扱いにしない。任意の不明項目を創作文で埋めない。
15. 外部情報取得の停止中も、公開済みcatalogの閲覧・既存在庫の判定を継続できる。
16. 画像権利や対象版が未確認ならその素材を公開せず、別モデル写真を無断代用しない。
17. job再送・途中再開・権限剥奪・複数編集者の競合で二重反映や失効権限の書込が起きない。
18. 大量import/media処理が予約APIの接続poolを枯渇させないことを測定する。
19. 受領前・検品前・貸出中の個体を、メーカー表の再取込でAVAILABLEへ戻さない。
20. 通常UIの全員総額・Regular/Premium差額・支払い直前HOLDが、サーバーの同じ条件と一致する。

## 10. サロモン・ChatGPT・オーナーの担当範囲

サロモンからは、蔵王2拠点へ入荷する数量とモデル名の原表を受け取る。詳細仕様・商品マスター・写真の提供まで入荷処理の開始条件にしない。既存ファイルを独自テンプレートへ打ち直させない。

ChatGPTが公式資料から商品リスト・詳細を整理する。モデル辞書は入荷表より広く保持できるが、当店在庫は入荷表・実受領から作る。型番等が含まれている場合は照合に利用し、不足する項目を全行に一律で追加要求しない。

オーナーはスキーの写真を用意する。全台数分のモデル説明入力や、未指定カテゴリーの写真準備まで担当を拡大しない。写真の名前・フォルダ・manifestから一括紐付け候補を生成し、曖昧なものだけ確認する。

入荷表だけでは年式・長さ・数量単位・店舗配分が確定できない場合、その不足だけを例外一覧として提示する。候補の比較、根拠、必要な確認を一度にまとめ、1モデルごとにChatGPTとCodexをオーナーが往復する方式へ戻さない。
